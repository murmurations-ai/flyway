§1 · what flyway is

A shared corridor — nothing more, nothing less.

The protocol that lets autonomous murmurations discover one another, recognize each other, exchange signals, and coordinate work — without surrendering sovereignty to a central controller.

flyway is

  • A small, typed protocol surface (9 tools, one agreement schema)
  • Runtime-agnostic — the same protocol over CLI, MCP, agent skill
  • Grounded in Sociocracy 3.0 as governance vocabulary
  • Git-as-system-of-record (each Source owns their repo)

flyway is not

  • A master controller above murmurations
  • A central server or required daemon
  • A harness-specific feature
  • A mechanism for forcing agreement between sovereign Sources
Lead by naming the negative space. People hear "AI agent protocol" and assume it's another orchestrator or marketplace — neither is what we're building. The distinction that matters most: peer coordination, not control. Each murmuration's Source keeps full authority; flyway is the explicit set of moves by which they meet at the boundary.
§2 · why it exists

Three forces, one missing piece.

1 · The world is becoming multi-agent

Agent swarms — Claude Code, Cursor, IDE agents, autonomous backends — are proliferating. Each has a human Source making decisions for it.

2 · Coordination needs a vocabulary

Without one, every cross-org collaboration reinvents how to surface a tension, propose action, integrate objections, and exit cleanly.

3 · No party should override another

Two Sources collaborating must keep their authority intact. Flyway gives them an explicit shape — consent rounds, signed proposals, named objections — instead of negotiating these ad-hoc.

The driver, in S3 form (because that's the vocabulary)

Conditions AI agent swarms proliferate; each is controlled by a human Source. Cross-org collaboration is becoming a daily occurrence (Andamio ↔ ODIN ↔ Chinook Wind ↔ external partners).
Effect Without a shared corridor, every collaboration reinvents identity, trust, signal transport, and decision rules from scratch. Coordination cost balloons; sovereignty gets compromised by whoever wires the bridge first.
Relevance A small, explicit protocol — adopted as a SKILL.md or MCP server — lets sovereign Sources meet at well-defined boundaries with cryptographic accountability on both sides.
The driver framing here is intentional. Newman has S3 fluency (or close to it from the Andamio context). Showing the driver in the canonical conditions / effect / relevance form signals that the protocol's vocabulary isn't aspirational — it's how we already think internally. If he pushes back on the framing, that's fine; the point is to demonstrate that the protocol's substance matches the substance of the problem.
§3 · the vocabulary

Source. Murmuration. Flyway.

TermMeaning
Source The human holding vision, authority, and accountability for an initiative. From Peter Koenig / Tom Nixon's Work with Source: the person who first takes the initiative and the risk on an idea.
Murmuration An agent swarm controlled by a Source. A murmurations-harness installation, a Claude Code session with subagents, a Cursor workflow, an OpenClaw agent — or a Source scripting agents directly against an LLM API. Runtime is irrelevant.
Flyway Ornithology term for a shared migration corridor used by many independent flocks. The intended posture: shared route, no central authority, autonomy preserved, coordination by agreement.
Three definitions that anchor everything else. The Source concept is doing a lot of work — it's the answer to "who's accountable?" in a world where agents act under human authority. The murmuration framing means we don't have to care which runtime someone uses. The flyway metaphor came from the migration corridor — many independent flocks, same sky.
§4 · the substance

Sociocracy 3.0 is the governance vocabulary.

Patterns from S3 are baked into the protocol surface as named tools and structured fields. Not aspirational — the schemas refuse to advance without them.

What S3 contributes

  • Tension — observable conditions + anticipated effect (§IV.1.2)
  • Driver — what motivates action (§IV.1.3)
  • Proposal staging chain — driver → requirements → draft → refinement → final (§IV.1.9-1.10)
  • Consent decision — accept / object (with reason) / exit (§IV.1.5)
  • Concerns to record — Step 9 of the consent round (§IV.1.5)
  • Agreement contract — driver, purpose, expectations, decision rule, review, exit (§IV.7.1)

Why this matters for review

Newman will recognize these because Andamio runs on the same vocabulary. The bet is that adopting flyway between organizations doesn't require new conceptual work — it's the same patterns we already use, made machine-readable.

The protocol enforces them: refinement can't happen without a prior draft; object requires a non-empty reason; a transfer requires a named recipient.

The S3 grounding is in ADR-0005. If Newman pushes on "why not a fresh decision vocabulary?" — the answer is: because the wheel is already invented and the people we want to collaborate with already speak it. Show ADR-0005 in the repo if needed.

The "9 tools defined once" line is load-bearing for the architecture story. The CLI is the same 9 tools wrapped in short verbs; the MCP server is the same 9 tools exposed via tools/list and tools/call. Adding a new runtime = wrapping the existing surface, not reimplementing.
§6 · the architecture

Five packages. Pure core, delivery adapters.

flyway-core (pure)

  • Types, schemas, JSON Schema tool definitions
  • Signing primitives (Ed25519, domain separation, canonicalization)
  • Pure functions: createTension, createProposal, createProposalResponse, recognizePeer, flywayInit, flywayStatus, flywayCheck
  • Runtime-agnostic — no Node-only deps in the hot path

Delivery adapters

  • flyway-agent — Agent Skills IO SKILL.md generator
  • flyway-mcp — stdio MCP server (stateless)
  • flyway-cli — terminal verbs (flyway init, recognize, tension, respond, propose, check, status)
  • flyway-harness — adapter for murmurations-harness (stub)

On-disk shape inside each Source's repo

.well-known/did.json                                            ← identity (W3C DID)
flyway/entity-statement.json                                    ← signed Source metadata
flyway/keys/source.key                                          ← private key (gitignored)
flyway/peers.yaml                                               ← signed recognition entries
flyway/peers/<host>/<owner>/<repo>/                              ← per-peer cached did.json + entity-statement
flyway/inbox/<sender-segments>/<id>.yaml                         ← received signals
flyway/outbox/<recipient-segments>/<id>.yaml                     ← sent signals (audit trail)
flyway/unrecognized/<safe-did>.yaml                              ← signed unrecognition records
flyway/agreements/<id>.yaml                                      ← byte-identical co-signed agreements (pending)
Two big points here. First: core is pure. The same logic runs from the CLI, from the MCP server, from a future SDK — there's no I/O in the hot path. Second: the repo IS the state. There's no database, no server, no daemon. Everything a peer needs to verify you is in your repo; everything you need to verify them is cached at recognition time in yours.
§7 · the crypto spine

Cryptography enforces the invariants at the boundary.

PropertyWhat it means
Self-attestation Every entity statement is signed by its own Source's Ed25519 key. No statement is trusted without verification.
Domain separation Each artifact kind has its own domain tag (flyway-v1:tension, flyway-v1:respond, etc.) so a signature over one kind can't be replayed as another. Catches kind-spoofing attempts at the verifier.
Canonicalization (JCS-style) Sorted-keys JSON, no whitespace, undefined dropped. Deterministic across implementations.
Antecedent verification (ADR-0009) A signer never signs an attestation over an unverified prior artifact. Enforced in core, not at the adapters. Surfaced as a security finding in this cycle; landed as a load-bearing architectural rule.
Path-traversal safety Peer DIDs become directory names — so peerCachePathSegments rejects .., /, NUL, and anything outside [A-Za-z0-9._-]. Found by the security review.
Recognition-window ordering A signal sent before the peer was recognized cannot retroactively become valid. flyway_check flags it.
Pluggable signers (ADR-0007) Local Ed25519 default; future Cardano-resident signer / KMS / HSM plug in without touching core. On-chain anchoring is optional.
The spine to highlight: ADR-0009. The class of bug it closed was subtle and real — the responder was verifying the subject signature against a freshly-read peer document from a path the peer controls. The fix is structural: verification moved into the signing primitive in core, with the recognition-time-cached DID document as the only acceptable verifying key. Adapters can't skip it because they can't sign without it. Worth pausing on if Newman wants depth.
§8 · a real consent cycle

An end-to-end exchange, signed all the way down.

This ran in 12 seconds on a laptop yesterday — verbatim from the smoke test.

1A → tension → B  conditions: sprint reviews running long; effect: retros getting skipped
2B → respond[acknowledge] → A
3A → propose[driver, type=directive] → B  refs.tensionId = (1) — promotes the tension
4B → respond[object] → A  reason: need agenda buy-in; concernsToRecord: [verify cadence, async option for EU]
5A → propose[draft] → B  integrates B's first objection
6B → respond[object] → A  concernsToRecord: bake-in facilitator rotation
7A → propose[refinement] → B  integrates the second objection
8B → respond[accept] → A  concernsToRecord: revisit cadence at month 1

After this, both sides hold 4 signed envelopes each — A in outbox (sent) + inbox (received), B mirror. flyway_check on either side reports 4 of 4 signals verified, 0 issues.

What's notably not there: no central database, no shared server, no trust in a third party. Each Source can independently audit the exchange against artifacts they themselves signed or attested to at recognition time.

This is the proof. If Newman wants to see it run, the Tier 3 walkthrough has the full verbatim transcript at docs/walkthroughs/2026-05-25-tier3-signal-dialogue.md. The full consent cycle (steps 3-8) ran for the first time yesterday during S+5a. It works.

§12 · feedback & discussion

Decisions I'd most want your push-back on.

Architectural bets

  • Agent skill as the primary protocol interface (ADR-0004) — is this the right bet? CLI + MCP are wrappers.
  • Antecedent verification in core, not at adapters (ADR-0009) — load-bearing rule; surfaces a class of bugs that's otherwise easy to miss.
  • Local-fs as the first transport (ADR-0008) — pragmatic for the demo; GitHub-PR is reserved. Is the priority right?
  • 9-tool surface — right granularity? Too few? Too many? Should recognize + unrecognize be one tool? Should propose + respond be split per kind?

Open questions for v0.2

  • Multi-party consent (#5) — parallel? pairwise? round-robin?
  • Facilitator role (#4) — currently not first-class. Should it be?
  • Chain integration — Cardano anchoring is optional (ADR-0007). When does it become mandatory?
  • Discovery model — central directory? Federated? Word-of-mouth via existing peers?
